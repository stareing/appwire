# 18 用户闭环：看得见、改得回、卡住时知道找谁、需求能回流（计划）

> 状态：计划（2026-10-02）。站在最终用户角度检查"万物皆工具"是否闭环：发现 → 执行可见 → 结果 → 失败转人 → 纠错 → 回流。
> 第 13–17 项已规划的条目只引用、不重复定义；本文件只负责差距分析与任务拆分，实施结果写入 `TASKS.md` 第 18 项。

## 0. 结论

机制层（声明、发现、唤醒、调用、导出）已完整，用户闭环有四处断口：**对外承诺与现行职责划分不一致**、**没有"需要用户本人操作"的失败类别**、
**用户需求不会回流给 App 开发者**、**理念只覆盖"能做"，未覆盖"看得见、改得回"**。另有一项需机主决定：用户级暴露开关。

## 6. 方案与任务

- **L1 修正对外承诺**（已完成，824204b）：README 卖点、原则 7、FAQ、对比表改为与 K2 一致——原则 7 改为"描述不是授权；放行由 Agent 决定，最终确认由 App 负责，
  AppWire 如实传递声明并保护资源"；10 种语言版本与 `llms.txt` 同步。
- **L2 需要用户操作的错误类别**（已实施，fe622b9）：协议新增 `USER_ACTION_REQUIRED`（-32019；登录过期、系统权限未授予、需切到前台、需在 App 内确认），
  携带面向用户的中文说明与可选的 App 内入口；App 可同时在自身界面提示。定义在 `spec/protocol.md` 第 4 节错误类别表；
  MCP 错误文本保持 `KIND: message`，说明之外的字段（如 `reason`、`uri`）只在 `structuredContent.error.details`；App 的所有错误回复都计入 `max_result_bytes`（第 14 项 S4）；
  各语言 SDK 暴露对应错误构造；Hub 原样转为 MCP 错误结果。
- **L3 缺失能力信号**：基于第 11 项调用日志统计 ① 不存在的工具 / 检索未命中 ② 参数校验失败率高的工具 ③ 被撤销次数多的工具；
  在 `doctor`（含 `--json`）与 Y2 DevTools 展示给 App 开发者。
- **L4 理念补齐**（已完成，824204b）：README 增加第 9 条原则"AI 的每次操作用户都看得见；声明了可撤销的就能撤回"，使第 15 项 X1 / X2 / X3 成为理念要求；10 种语言同步。
- **L5 用户级暴露开关（2026-10-02 决定实施；命令行入口已随第 16 项 P2 完成，fe622b9；按 Agent 拒绝待 P1，托盘入口待 X3）**：按 App / 工具对所有 Agent 隐藏，或对指定 Agent 拒绝调用。机制即第 16 项 P2（`hide` 全局、`deny` 可按 Agent），
  此处不另行定义；用户入口为 `app-mcp-host policy` 子命令与 X3 托盘开关。

## 7. 顺序与验收

顺序：L1 → L2 → 第 15 项 X1 + 第 11 项调用日志 → L3 → 第 15 项 X2 → 第 15 项 X3（附带 L5 的托盘入口；L5 的命令行入口随第 16 项 P2）；L4 与 L1 同批。

验收：
- README 及 10 种语言版本、`llms.txt` 不再出现"Hub 审批"承诺。
- App 抛出 `USER_ACTION_REQUIRED` 时，Claude Code 中用户能看到 App 给出的说明（U1 验证后）；各 SDK 有构造该错误的测试。
- `doctor` 列出最近窗口内的不存在工具名、校验失败率与撤销次数，数据只在本地。
