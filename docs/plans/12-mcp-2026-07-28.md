## 0. 结论

1. **不需要升级 rmcp。** 项目锁定的 rmcp 3.5.0（`Cargo.lock`）是 crates.io 当前最新版（`max_stable_version = 3.5.0`，2026-09-28 发布），
   自 3.0.0（2026-07-28）起已实现 2026-07-28：`server/discover`、每请求 `_meta`、`subscriptions/listen`、SEP-2243 请求头校验、
   MRTR、`CacheableResult`；Streamable HTTP 服务与 stdio 服务端都是**双版本**（legacy 走会话，modern 走无状态）。
2. **现在 Hub 主动把自己限制为旧版本。** `crates/hub/src/mcp.rs` `get_info` / `supported_protocol_versions` 只声明到 `2025-11-25`；
   实测对 2026-07-28 请求（含 `server/discover`）一律返回 `400` + `-32022 UnsupportedProtocolVersion`（`supported` 只含旧版本）。
   这是合规的“legacy-only 服务器”行为，旧客户端与能回退的新客户端照常可用；问题是新客户端只能走即将被淘汰的会话路径。
3. **真正的工作量在 Hub 的会话语义，不在传输。** 2026-07-28 删除了协议级会话（SEP-2567），并规定 `tools/list` 等列表
   **不得按连接变化、不得因其他请求的副作用而变化**。本项目有 4 处按 MCP 会话保存的状态（`SessionState`：`apps.select` 选择、
   总览首次附带、租约、渐进暴露已展开集合）以及按会话变化的 `tools/list`（3.7 渐进暴露）。rmcp 对 modern 请求**每个请求调用一次工厂**
   新建 `McpSession`，直接打开 2026-07-28 会让这些状态每请求丢失。必须先为 modern 客户端重新定义这些语义（第 3 节），再放开版本。
4. 建议：保持**双版本（dual-era）**——旧客户端完全不变（仍用会话），新客户端走无状态语义；分三部分实施，排在 4e 之后、
   与 4c 的 F（Hub 渐进披露）合并设计（第 6 节）。

## 3. 版本协商与向后兼容策略

### 3.1 版本与路由

- **声明**：`supported_protocol_versions` 改为 `known_up_to(V_2026_07_28)`（含全部旧版本）；`get_info` 的 `protocol_version` 保持
  `LATEST_WITH_INITIALIZE`（rmcp 文档：回复 `initialize` 只能给出带握手的版本，`[R] model.rs:186-202`）。
- **HTTP（`/mcp`）**：保持 `legacy_session_mode = true`。rmcp 按请求分流（`[R] tower.rs:390-445, 2225-2260`）：
  `initialize` 一律走 legacy 会话；带完整 2026-07-28 `_meta` 的请求（及 `server/discover`）走无状态路径。同一端点同时服务两代客户端
  （规范允许：[versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) “A dual-era server MAY serve both eras concurrently on the same endpoint”）。
- **stdio（`serve_stdio`）**：rmcp 的 `serve_server` 首条消息若不是 `initialize` 且带完整 modern `_meta`，按 modern 处理（`[R] service/server.rs:571-615`）；
  stdio 是单客户端进程，会话状态以进程为界，与现状一致。
- **Router 层不变**：Origin 403 → 令牌 401 的顺序先于 rmcp（`http_server.rs:273-284`），modern 与 legacy 同样适用。
- **回退开关（P-10）**：配置项 `mcp.max_protocol_version`（`"2025-11-25"` / `"2026-07-28"`，`app-mcp-host` 配置与 `--mcp-max-protocol`；
  Hub 各语言绑定同步），设为 `2025-11-25` 即恢复当前行为（P1 的 `-32022` 应答，客户端回退 legacy）。
  第一部分默认仍为 `2025-11-25`，第二部分验收后改为 `2026-07-28`。

### 3.2 无状态语义（modern 客户端）

判定：handler 内 `RequestContext::protocol_version()`（`[R] service.rs:1233-1240`）`!has_initialize()` 即 modern。
`McpSession` 拆为两种模式：legacy（现状，会话号 + Drop 清理）与 stateless（不登记 peer、不分配会话状态、Drop 无副作用）；
工厂无法预知请求的版本，因此 `McpSession::new` 不再在构造时登记任何东西（现在已是如此），Drop 清理只在 `on_initialized` 发生过时执行。

| 会话状态 | legacy（不变） | modern（新定义） |
|---|---|---|
| `tools/list` 渐进暴露（3.7） | 内置 + 本会话已展开 / 调用过 / 选定的 App | **不随请求副作用变化**：生效时 = 内置 `apps.*` + `Hub::select_instance` 全局选定的 App（由厂商 / 用户经 Hub API 改变，属于服务器状态而非会话）；未生效时 = 全部。`apps.tools` 只返回 schema，不改列表 |
| 调用未列出的工具 | 按全名路由（3.7“路由不变”） | 同左；若客户端拒绝调用未列出的工具（U3），新增内置 `apps.call {tool, arguments}` 作为通用入口（只增，两代都可用） |
| `apps.select` | 本会话选择 | 显式句柄：`apps.select` 返回 `selection`（≥128 bit 随机、TTL 与上限，过期给出可恢复的错误信息，SEP-2567 指南）；`apps.call` / 带 `selection` 时按其路由；不带时按现有默认实例规则 |
| 总览首次附带（protocol 7.2） | 每会话首次接触某 App 附带 | `server/discover.instructions` 给出 App 一句话简介；`apps.tools` 结果附带该 App 总览；工具调用不再自动附带（无会话可去重，避免每次调用重复附带） |
| 租约（lifecycle 4.2） | 会话关闭时收回 | 只按 TTL 到期；租约键 `mcp`（所有 modern 请求共享一个调用方键）。与 4e B2“按（会话, App）自适应租约、会话结束即收回”冲突，见第 6 节 |
| 资源订阅 | `resources/subscribe` | `subscriptions/listen` 的 `resourceSubscriptions`；订阅随流关闭结束；仍保留“上游资源不支持订阅”的规则（不在 ack 中返回） |
| list_changed 通知 | 经会话 peer 发送 | 只发给 `toolsListChanged` / `resourcesListChanged` 订阅流；只在服务器状态（App 连接、注册、全局选择）变化时发 |
| 审批 `ApprovalRequest.session` | `mcp:<n>` | `mcp`，并在 `ApprovalRequest` 中附 `clientInfo.name`（仅显示用；规范：`clientInfo` 自报不可信，不用于决策） |
| 日志 `cid` | `mcp-<n>` | `mcp-r<n>`（每请求一个），日志同时记 `clientInfo` 与 JSON-RPC id |
| `HubStatus.mcp_sessions` | 会话数 | 保持含义；另加 `mcp_listen_streams`（活跃订阅流数），只增字段 |

说明：clientInfo 不作为状态键（规范要求客户端 SHOULD NOT 依据 serverInfo 改变行为，对称地 clientInfo 也是自报信息，不可信）。
`Hub::reset_session` / API 会话（`api:<id>`）不受影响。

## 4. rmcp 升级路径与风险

- **版本**：本地 3.5.0 = crates.io 最新（2026-10-02 查询 `crates.io/api/v1/crates/rmcp`）。2026-07-28 支持始于 3.0.0（2026-07-28 发布，
  `[R] CHANGELOG.md:159`），之后 3.1～3.5 均为修复与补充（3.2.0 “keep initialize on legacy protocol versions”、“allow concurrent streamable http requests”；
  3.3.0 `negotiate_initialize`；3.4.0 `ServerConfig` / `ClientConfig`，弃用 `ServerInfo` / `ClientInfo` 别名；3.5.0 `LATEST_WITH_INITIALIZE`、拒绝重复 SEP-2243 头、
  `cacheScope` 容错、保留显式 `null` 的 `structuredContent`）。**本计划不需要改 `Cargo.toml` / `Cargo.lock`。**
- **API 面（3.5.0，已在用或将要用）**：`ServerHandler::{supported_protocol_versions, discover, accepted_subscription_filter, listen}`；
  `subscribe` / `unsubscribe` 已标 `#[deprecated]`（legacy 专用，mcp.rs 现有 `#[allow(deprecated)]`）；`SubscriptionContext`；
  `RequestContext::{protocol_version, client_info}`；`ListToolsResult::with_ttl_ms`、`cache_scope`；`StreamableHttpServerConfig::{legacy_session_mode, json_response, with_allowed_origins, with_stateless_protocol_metadata_required}`；
  客户端 `ClientLifecycleMode::{Initialize, Discover, Auto}`（`ServiceExt::serve` 仍是 legacy，`[R] service/client.rs:636-656`）。
- **上游客户端**：保持 `serve`（legacy）即可连接 legacy 与 dual-era 上游；modern-only 上游需 `ClientLifecycleMode::Auto`（先 `server/discover`，失败回退）。
  Auto 模式下上游的 list_changed 需要客户端侧 `subscriptions/listen`，rmcp 客户端对此的封装**未核实**（U4）→ 列为第三部分可选项。
- **风险**：
  - rmcp 无状态路径**每请求调用工厂**（`[R] tower.rs:1420-1423, 2257-2259`）——现有 `McpSession` 的构造 / Drop 副作用必须先改（第一部分）。
  - `tool_schemas` 缓存按工具名永久保存（不随 `tools/list_changed` 失效），且查询时也调用工厂。Hub 不用 `x-mcp-header`、`get_tool` 返回 `None`，
    影响仅限“构造一个空 `McpSession`”；剔除 App schema 中的 `x-mcp-header` 后无功能影响。
  - rmcp 后续小版本可能调整双版本行为：Cargo 用 `"3.5"`（允许 3.x 升级），任何 `cargo update` 后必须跑第 5 节的协议测试。

## 5. 实施拆分

所有部分：只改 `crates/hub`（`mcp.rs`、`hub.rs`、`http_server.rs`、`call.rs`、`upstream/`）、`crates/host`（配置 / CLI）、Hub 绑定（只增配置字段）、
`spec/hub-api.md`、`spec/protocol.md`、`e2e/`；不改 SDK ↔ Host 协议（`crates/protocol` 的消息与 `app/*` 方法不变）。

### 第一部分：双版本基础（默认仍 legacy）

- 范围：`McpSession` 拆 legacy / stateless 模式（Drop 只清理登记过的会话）；版本上限配置与回退开关（3.1）；`ttlMs` / `cacheScope`（m5）；
  `tools/list` 确定性排序（m3）；剔除 App / 上游 schema 中的 `x-mcp-header`（m4）；资源不存在按版本选码 + 修复 `-32002` 反查缺陷（m6）；
  `resultType` 核查（M8）；spec/protocol.md 10.1 写明 `-32016`～`-32019` 约束（m10）。
- 测试：hub 单元——版本上限为 2025-11-25 时 modern 请求得 `-32022`（锁定 P1 现状）；上限为 2026-07-28 时 `server/discover` 返回 `supportedVersions` 含两代、
  `instructions` 非空、`serverInfo` 在 `_meta`；连续 N 个 modern 请求不新增 / 不删除任何 `SessionState`；列表两次逐字节相同；
  `x-mcp-header` 被剔除；`-32002`（上游）→ `ResourceNotFound` 回归测试；modern / legacy 资源不存在码分别为 `-32602` / `-32002`。
  集成：`crates/hub/tests/it/mcp_ipc.rs` 增加 rmcp 客户端 `ClientLifecycleMode::Discover` 用例（IPC 上的 `/mcp`）。
- 验收：`cargo test -p app-mcp-hub -p app-mcp-host`、`cargo clippy --workspace --all-targets` 0 警告；默认配置下 e2e 12/12 不变。

### 第二部分：无状态语义 + `subscriptions/listen`，默认开启 2026-07-28

- 范围：3.2 全表（渐进暴露的 modern 列表、`apps.call`、`apps.select` 句柄、总览改经 discover / `apps.tools`、租约键、审批 session、`cid`）；
  `accepted_subscription_filter` / `listen`，Hub 订阅者从会话号泛化为订阅 ID，list_changed / resources/updated 双路径发送；
  取消语义验证（m-cancel）；默认上限改为 2026-07-28；spec/hub-api.md 3.6 / 3.7 / 3.9、spec/protocol.md 7.2 改写为“两代分述”；
  Hub 绑定（C / Node / uniffi）新增 `mcpMaxProtocolVersion` 配置（只增）。
- 测试：hub 集成——modern 客户端（rmcp Discover 模式）：列工具、调用、`apps.select` 句柄路由与过期错误、listen 收到 App 连接后的 `tools/list_changed`
  与资源 `updated`、断开流后订阅释放；legacy 与 modern 客户端并发连接同一 Hub 互不影响（legacy 会话状态不被 modern 请求改变）；
  调用中断开流 → App 收到 `call/cancel`。e2e：`e2e/src/mcp-client.ts` 增加 modern 模式（`_meta`、`MCP-Protocol-Version`、`Mcp-Method`/`Mcp-Name`、
  listen 流），`m1.test.ts` 关键用例两代各跑一遍。
- 验收：cargo / pnpm 全量测试与 clippy 0；用本机 Claude Code（2.1.281）实测：Host 日志中 `server/discover` 与无 `Mcp-Session-Id` 的请求、
  工具调用成功、App 上下线后工具列表刷新；回退开关设为 2025-11-25 后 Claude Code 仍可用。

### 第三部分（可选增强，按需另开）

- 上游客户端 `ClientLifecycleMode::Auto`（支持 modern-only 上游，U4 核实后）；
- 第 11 项 tracing：从 `_meta.traceparent` 继承调用链（m2）；
- 无 `ApprovalHandler` 时用 MRTR form elicitation 向用户确认（M7，需幂等设计）；
- 长时间唤醒的调用使用 tasks 扩展（M6）。
